# 1. Purpose & Usage

The Decision Log is a living document that records every significant architectural, product, AI governance, and ethical decision made during the build of Valtara Executive OS (VEX-OS). It provides an auditable trail of why the system is built the way it is — not just what was built.

Every engineer, product manager, and governance reviewer must add an entry to this log for any decision that: (a) establishes a constraint on the system; (b) selects a technology, framework, or vendor; (c) resolves a significant design trade-off; or (d) overrides a default specified in the pre-build documentation suite.

| Decision ID Format | DL-[CATEGORY]-[NUMBER]: DL-ARCH (architecture), DL-PROD (product), DL-AI (AI/governance), DL-SEC (security), DL-INFRA (infrastructure) |
| ------------------ | -------------------------------------------------------------------------------------------------------------------------------------- |
| Status values      | Proposed → Under Review → Decided → Implemented → Superseded                                                                           |
| Entry ownership    | Decision maker owns the entry; Engineering Lead reviews all DL-ARCH entries; CAO reviews all DL-AI and DL-SEC entries                  |

**DL-ARCH-001 — Architecture Pattern — Layered Monolith for MVP**

| Date               | August 2026                                                                                                                                                                                                                                                                                                                                                                                                          | Decision Maker | Francis Ogbogu — CAO |
| ------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------- | -------------------- |
| Decision           | VEX-OS v1.0 will be built as a layered monolith with clean internal boundaries, not a microservices architecture.                                                                                                                                                                                                                                                                                                    |
| Options Considered | (A) Microservices from day one. (B) Layered monolith with extraction path. (C) Serverless functions.                                                                                                                                                                                                                                                                                                                 |
| Rationale          | Microservices add operational complexity (service discovery, distributed tracing, deployment orchestration) that is disproportionate to the team size and product maturity at MVP. Option C (serverless) introduces cold-start latency incompatible with the ≤2s dashboard load requirement. |
| Consequences       | Faster development velocity at MVP. Simpler local development (Docker Compose). Service extraction possible in v2 without breaking changes if clean boundaries are maintained from Sprint 1. Engineering must enforce boundary discipline — cross-layer direct dependencies are prohibited.                                                                                                                          |
| Status             | Decided                                                                                                                                                                                                                                                                                                                                                                                                              |

**DL-ARCH-005 — HITL Enforcement Point — Application Layer**

| Date               | August 2026                                                                                                                                                                                                                                                                                                                                                                                                                                           | Decision Maker | Francis Ogbogu — CAO |
| ------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------- | -------------------- |
| Decision           | HITL governance is enforced at the application layer. Agents cannot bypass the HITL queue regardless of task type or instruction.                                                                                                                                                                                                                                                                                                                     |
| Options Considered | (A) Enforce HITL within agent logic (trust agents to self-enforce). (B) Enforce at application layer with database constraint.                                                                                                                                                                                                                                                                                                                        |
| Rationale          | Option A (agent self-enforcement) is unreliable — an incorrectly prompted agent or a future prompt change could inadvertently bypass HITL. HITL is a hard safety requirement, not a behavioral guideline. Option B (application layer + database constraint) makes bypass architecturally impossible: no external action record can be created without a linked approved HITL queue record. This is enforced regardless of what the agent logic does. |
| Consequences       | Absolute HITL guarantee. Agents can be retrained, re-prompted, or modified without risk of bypassing the governance layer. HITL compliance is testable independently of AI behavior.                                                                                                                                                                                                                                                                  |
| Status             | Decided                                                                                                                                                                                                                                                                                                                                                                                                                                               |

**DL-SEC-001 — JWT Signing Algorithm — RS256, Not HS256**

| Date               | August 2026                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              | Decision Maker | Francis Ogbogu — CAO |
| ------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------- | -------------------- |
| Decision           | Access and refresh JWTs are signed with RS256 (asymmetric), using a `JWT_PRIVATE_KEY`/`JWT_PUBLIC_KEY` keypair — apps/web's `auth.ts` (NextAuth v5) is the sole issuer; apps/api's JWT middleware verifies with the public key only.                                                                                                                                                                                                                                                                                                                                                                                                                     |
| Options Considered | (A) HS256 with a single shared `JWT_SECRET`/`JWT_REFRESH_SECRET`, as VEX-OS-API-001 §5's literal `.env` template implies. (B) RS256 with a private/public keypair, per VEX-OS-SEC-001 §3.1's explicit "RS256 signed" requirement for both access and refresh tokens.                                                                                                                                                                                                                                                                                                                                                                                     |
| Rationale          | SEC-001 §3.1 states the JWT structure requirement explicitly and without qualification ("Security is an architectural constraint... no security control may be deferred without explicit Decision Log entry and CAO risk acceptance"), while API-001's `.env` template just wasn't updated to match — a stale-draft inconsistency between two governance docs, not a real design choice. RS256 also means only apps/web (the issuer) ever holds the private key; apps/api and any future verifier-only service holds only the public key, so a compromise of the API tier alone can't be used to forge tokens the way a shared HS256 secret would allow. |
| Consequences       | `.env.example` carries `JWT_PRIVATE_KEY`/`JWT_PUBLIC_KEY` beyond the literal API-001 §5 template (documented inline there, pointing back to this entry). Signing/verification uses the `jose` library. This entry was originally referenced from `.env.example` at Sprint 1 but never actually logged here until Sprint 6 — backfilled now for governance-suite accuracy, not because the decision changed.                                                                                                                                                                                                                                              |
| Status             | Decided                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |

**DL-SEC-002 — Administrator Role Provisioning — `ADMIN_EMAILS` Allowlist**

| Date               | August 2026                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            | Decision Maker | Francis Ogbogu — CAO |
| ------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------- | -------------------- |
| Decision           | A session is minted with the Administrator role at sign-in when its email exactly (case-insensitively) matches an entry in the `ADMIN_EMAILS` environment variable (comma-separated), checked in `resolveRoleForEmail` before the existing Executive/Delegate checks. No other path in the product can grant Administrator.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| Options Considered | (A) An invite-and-accept flow mirroring the Delegate relationship (`delegate_links`). (B) A role column settable only via direct database access. | Rationale          | Administrator is an operational role with system-wide reach (SEC-001 §3.2: audit export, user role management, no executive-content access) — this is the first Sprint 6 feature that actually needs one to exist, since nothing in the product could grant it before now. If a future sprint needs in-product Administrator management (SEC-001 §3.2's "user role management" duty, itself still unbuilt), that would supersede this entry.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |

**DL-SEC-004 — Postgres Privilege Separation — Restricted `vexos_app` Runtime Role**

| Date               | August 2026                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           | Decision Maker | Francis Ogbogu — CAO |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------- | -------------------- |
| Decision           | The application's runtime `DATABASE_URL` connects as a new restricted role, `vexos_app` (provisioned by `migrations/0006_app_role_privilege_separation.sql`), which has ordinary CRUD on every table except `audit_log_entries` — INSERT/SELECT only there, with UPDATE/DELETE explicitly revoked. A separate `DATABASE_MIGRATION_URL` (the existing bootstrap role) is required to actually run migrations, since `vexos_app` deliberately holds no DDL or `CREATEROLE` rights.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| Options Considered | (A) Leave the application connecting as the bootstrap role (status quo). (B) Provision a restricted role and grant it table-by-table as each migration adds tables. (C) Provision a restricted role once, using `ALTER DEFAULT PRIVILEGES` so every _future_ table a migration creates automatically inherits the same grants with no per-migration action required.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| Rationale          | Option A is what caused this entry to exist: Docker's official postgres image always bootstraps `POSTGRES_USER` as a cluster superuser, and Postgres superusers bypass row-level security unconditionally — including `FORCE ROW LEVEL SECURITY` — so `audit_log_entries`' tamper-proofing (SEC-001 §6) was not actually enforced under the connection both `docker-compose.yml` and CI used. Option B works but is a discipline problem waiting to happen — a table added by a future migration silently has no grant, and no test would necessarily catch that until someone tries to use it. Option C (chosen) makes correctness the default: `ALTER DEFAULT PRIVILEGES FOR ROLE CURRENT_USER` captures whichever role actually runs the migration (locally, in CI, or in a future production deploy — deliberately not hardcoded to one role name) and extends the same grants to `vexos_app` automatically, with `audit_log_entries` carved out as the one deliberate exception. |
| Consequences       | Every environment needs two connection strings instead of one (`DATABASE_URL` for the app, `DATABASE_MIGRATION_URL` for `npm run db:migrate`) — documented in `.env.example` and `VEX-OS-DOG-001`. `packages/database/src/__tests__/audit-log-immutability.test.ts` now proves the real guarantee in CI, not a documented bypass. Production (Supabase) needs the equivalent role provisioned and its own `DATABASE_URL` pointed at it — the migration is portable (no hardcoded role names beyond `vexos_app` itself) but still needs to actually run there.                                                                                                                                                                                                                                                                                                                                                                                                                         |
| Status             | Decided                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
